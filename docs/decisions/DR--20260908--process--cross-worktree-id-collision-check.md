# Cross-worktree ID collision check: a `buildy` pre-dispatch gate, not an nwave-ai patch

## Context

nWave's DESIGN and DISCUSS waves each allocate a new sequential identifier — an ADR number
(`docs/product/architecture/adr-*.md`) or a story ID (`US-N`) — by globbing the current working
tree for the highest number already in use. That glob only sees the calling worktree. Two
worktrees branched from the same commit, each starting an independent feature, both glob to the
same "highest number taken" and both allocate the next one — an invisible collision until merge,
by which point both sides have commits and cross-references built on the now-duplicate ID.

The allocation logic itself lives in nwave-ai's vendored wave skills (e.g.
`nw-design/SKILL.md:67`), not in this repo. Somewhere, a placement had to be chosen for the fix.

## Options Considered

### Option 1: Patch the wave skill's allocation logic upstream

Change the glob in `nw-design`/`nw-discuss` to check across worktrees before allocating.

- Fixes it at the source, for every caller, not just `buildy`.
- Not our code to patch. `~/.claude/skills/nw-*` is generated by `nwave-ai install`, and the public
  `nWave-ai/nWave` repo is itself "a generated projection of a private dev repo" (root `CLAUDE.md`)
  — a local edit is silently overwritten on the next install, and a PR against the public repo
  isn't confirmed to be nWave's actual contribution path.

### Option 2: Manual discipline — check before starting parallel worktrees

Rely on the human to `git log`/`ls` sibling worktrees before kicking off a second feature.

- Zero implementation cost.
- Is exactly the failure mode that prompted this DR: the check is easy to forget precisely because
  the collision stays invisible until merge, long after the moment it would have been cheap to
  catch.

### Option 3: Pre-dispatch gate in `buildy`

Add a checkpoint `buildy` runs itself, before handing off to the DESIGN or DISCUSS wave agent —
the same shape as the existing `DELIVER_PENDING` cost-check gate. `git worktree list --porcelain`
to enumerate sibling worktrees, glob each one's ID files (including uncommitted/untracked, since a
colliding number can exist before either side commits), and compare against what this worktree is
about to allocate.

- Buildy already owns "checkpoints *around* wave dispatch" by charter (`buildy/SKILL.md`'s opening
  line) — this is squarely that, not a reimplementation of wave logic.
- Only protects features routed through `buildy`. A wave invoked by hand, outside this skill,
  isn't covered.
- Requires deciding what happens on a detected collision (see below).

## Decision

**Option 3.** Add `ID_COLLISION_CHECK` to `buildy`'s state machine, firing inside `IN_WAVE`
specifically before DESIGN or DISCUSS dispatch. On a detected collision: **surface and stop** —
report the conflicting worktree and number, then wait for the human to resolve it. Never auto-bump
the number in either worktree; a third worktree could be racing the same check, and the two
sequential-ID waves are already the human's domain for the actual value chosen (`buildy`'s
`DELIVER_PENDING` gate uses the same "state the fact, let the human decide" shape — no gate in
`buildy` auto-resolves on the human's behalf).

## Exceptions

Revisit Option 1 if nwave-ai's actual contribution path becomes clear and the maintenance tax of
carrying this in `buildy` instead grows — but only through its own decision record, matching the
precedent in `DR--20260907--process--spec-ladder-placement.md` for not forking vendored nwave-ai
behaviour locally as a shortcut.
